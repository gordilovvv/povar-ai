# sema

## О проекте

Проект для **вечеринок**. Цель — убрать ручную работу и автоматизировать
общение с гостями через AI-агента.

## Claude разговорный режим

Отвечай кратко. Не превышай ~500 токенов, если я явно не попросил развёрнутый ответ.
В длинных сессиях используй короткие тезисы вместо больших абзацев текста.
Не выдавай длинные простыни текста в обычном разговоре. Держи ответы компактными.

### Уточняй на развилках

Если есть неоднозначность, развилка или не хватает факта — спрашивай, не угадывай. Один короткий вопрос дешевле неверного действия.

Перед запуском цикла разработки модуля обязательно задай уточняющие вопросы, если в задаче не определены: конечный результат (что считается «готово»), перф-бюджет, поведение при ошибках. Без этого не стартуй — цикл к неверной цели дороже вопроса.

Формат задачи на модуль: вход → выход → бюджет времени → негативные сценарии. Критерии e2e-теста берутся прямо из задачи, не выдумываются.

## Стек

typescript, pg + pg-format, Grammy, Zod, Pino + Pino Pretty. Менеджер пакетов PNPM

### Раскладка папок
- `src/Webhook.ts` — точка входа: принимает входящие вебхуки, кладёт сообщения в очередь. Отдельный процесс.
- `src/Worker.ts` — точка входа: разбирает очередь чатов, дёргает агента. Отдельный процесс.
- `src/Intelligence/` — AI-агент (Claude): `Agent.ts`, `system.md`, `Tools/` (инструменты агента).
- `src/Platforms/` — интеграции внешних каналов (`Whatsapp/`: парсинг, подпись, отправка).
- `src/Db/` — storage-слой (pg), по файлу на таблицу; пул в `Db.ts`.
- `src/Lib/` — утилиты общего назначения.
- `src/Dashboard/` — **отдельный проект** (админка). Поднимается своим процессом, со своими `Lib/`, своим `index.ts`-входом, своим `Db`/пулом. С основным кодом не переплетаем.

### Именование и импорты
- Папки и файлы `.ts` — **PascalCase** (`src/Db/WaChats.ts`, `src/Lib/Fmt.ts`, `src/Webhook.ts`). Исключения (lowercase): `index.ts`, `environment.ts` и все `.md` (`system.md`).
- Импорты — через subpath-алиасы `#*` (`package.json` → `imports`), не относительные пути: `#Db/Db.js`, `#Lib/Fmt.js`, `#environment.js`. Расширение в импорте всегда `.js` (резолвится в `.ts` в dev, в скомпилированный `.js` в проде).
- Ассеты (не-`.ts`, напр. `system.md`) `tsc` в `dist/` не эмитит — копируются отдельным шагом `build`.

## Код

### Классы

Константы, привязанные к классу, держим внутри класса как `private static readonly`, а не модульными `const` над файлом. Модульный уровень оставляем только для того, что реально шарится между модулями (экспортируемые типы, Zod-схемы, общие enum).

### Импорты

Внутренние модули — через subpath-imports (`#Раздел/Модуль.js`) с расширением `.js`, не относительными путями (`../`).

### Коментарии
Комментарии по дефолту не пишем. Можем написать только если видим, что логика плохо читается или какой-то неявный кейс.Также комментарии должны быть короткими и ясными. Запрещено делать комментарии на несколько строк.

План работы и TODO держим вне кода. Комментарий-«лесенку» из нескольких пунктов не пишем; максимум одна строка `// TODO: ...`.

### Структура и чистота
- Утилиты общего назначения не объявляем в рабочих файлах — выносим в `Lib/` отдельным файлом с понятным именем.
- Где жить коду решает природа кода, а не число вызовов. Логика, привязанная к одному контексту, — рядом с ним. Универсальная утилита, не завязанная на контекст, — в `Lib/` отдельным файлом, даже если потребитель пока один.
- Одноразовую линейную логику пишем инлайн — не выделяем функцию ради единственного вызова и не строим тонкие обёртки-цепочки. Это про локальную логику внутри функции; разбиение на слои остаётся обязательным даже при единственном вызове.
- Делаем ровно то, что просят. Меняем только названное; соседний код не трогаем, не переносим, не «улучшаем» заодно. Расширение scope — отдельным согласованием.
- Внешние/сырые данные не приводим к типу через `as` — парсим и валидируем (zod). `as` к доменному типу для непроверенных данных запрещён.
- Магические числа-параметры держим именованными константами рядом с местом использования; в конфиг выносим, только когда их реально нужно менять снаружи.
- Порядок в файле сверху вниз: основной флоу/хендлер — первым, вспомогательные функции — ниже него. Не заставлять читателя прыгать вверх к определениям.
- Инфраструктурное/транспортное (проверка подписи, парсинг протокола, низкоуровневый glue) — отдельным модулем, не инлайнить в бизнес-файл.
- Не плодим сущности: не заводим таблицу/колонку/абстракцию, если задачу решает существующая структура. Простейшая работающая модель побеждает; усложнение — обосновать, а не «так чище».
- Производное выводим из единого источника правды (например, карту весов — из порядка опций enum), а не дублируем литералы рядом

### Состояние, гонки, идемпотентность

- Состояние и замки держим в данных/SQL, не в памяти процесса. Захват работы — одним атомарным `UPDATE … RETURNING`, который сам себе замок (без in-memory Set, без watermark):
- Оптимистичное обновление при гонке на запись одной строки (несколько источников могут писать одновременно): версия-колонка. Читаем версию, пишем `update … set …, version = version + 1 where id = … and version = <прочитанное> returning *`. Ноль затронутых строк = нас опередили → перечитать и решить (повтор/пропуск), а не слепо перезатирать.
- Явное > неявное: идемпотентность и гонки — через `try/catch` на конкретный код ошибки (нарушение unique), а не `on conflict do nothing`.
- select-or-create через рекурсию: `select` → нет → `insert` → на unique-нарушении вызвать функцию заново; верхний `select` перечитает победителя гонки. Терминируется: после нарушения строка точно есть.
- Не ретраить, когда повтор вреден по смыслу (устаревшее действие вклинится в ушедший вперёд поток) → терминальный статус (`failed`), не назад в очередь.

### Ошибки: fail-fast

Ошибки не глушим. Нет осмысленной обработки — пусть летит наверх и роняет всё приложение (`process.exit(1)` с логом причины). Тихий `catch` с логом и продолжением работы — запрещён: молча деградировавший бот хуже упавшего.

### Переменные окружения

- Читаем **только** из `environment.ts` (экспорт `env`). `process.env` напрямую в коде не трогаем.
- Значения кред (`.env`) не смотрим — ни `cat`, ни `grep`, ни dump содержимого. Какие переменные есть — узнаём по `environment.ts`, а не по `.env`.
- В `environment.ts` пишем проще: каждая переменная просто `z.string()` (или `z.enum`), **без `.default()`**. Дефолты маскируют отсутствие конфига и выстрелят в проде — пусть лучше падает на старте.

### Handlers

Когда пишешь или правишь хендлер HTTP-запроса (новая ручка, файл в `Handers/`) — используй скилл `http-handler`. Все конвенции там.

- Query/path-параметры парсим хелперами из `#Libs/Fmt.js`.
- Даты гоняем через `#Libs/Fmt.js`: наружу `fromDateTime`, в базу `toDateTime`, всё UTC. `.toISOString()` инлайном не дёргаем.

### DB
Когда пишешь или правишь DB-код — storage-слой (`src/db/`), SQL, таблицу, миграцию или ручку, которая ходит в базу — используй скилл `db-code`. Все конвенции там.

Запросы к базе выполняешь сам через `./scripts/db.sh` (обёртка над `psql`, берёт `DATABASE_URL` из `.env`):
- `./scripts/db.sh "SELECT ..."` — выполнить SQL
- `./scripts/db.sh` — интерактивный psql

### Время

- Храним время UTC-строкой через `toDateTime`. Dubai (`getDubaiTime`) — только для показа агенту/человеку.
- Окна сравниваем в одном представлении: границу считаем тем же `toDateTime` (`toDateTime(Date.now() - N)`) и сравниваем со store-полем. Новую колонку-таймстамп ради окна не заводим.

### Логирование производительности
Замер времени выполнения через `process.hrtime()` — вызов до и после операции, вывод через `console.log` с тегом `[модуль]`, идентификатором контекста, кратким описанием операции и временем в формате `Xs Yms`.

## Самотестирование при разработке

Закончил модуль, handler, либу или заметный кусок логики — **обязательно вызови скилл `e2e-test`** перед отчётом пользователю.

**Определение «готово» (жёсткое, в т.ч. для /goal-цикла):** модуль готов и цель выполнена ТОЛЬКО когда пройдены все шаги:
1. `pnpm typecheck` и `pnpm lint` зелёные (`node:test` гоняет TS без проверки типов — красный tsc проходит мимо зелёных тестов);
2. позитив написан автором, `pnpm test` зелёный;
3. `e2e-critic` (adversary) вызван, сам написал и прогнал `tests/<module>.attack.e2e.test.ts` (auth / IDOR / инъекции / кривой ввод / гонки, красный-первым) И прочитал позитивный тест автора на самообман (сверка с БД, не ослаблен ли ассерт/данные/бюджет) — вернул **ГОТОВО** по обоим;
4. `simplifier` вызван на дифф модуля и теста.

Пока `e2e-critic` не дал `ГОТОВО` — рапортовать «готово» и завершать /goal-цель запрещено. `НЕ ГОТОВО` = цикл не закрыт: чинишь код (не ослабляешь пробу) и гоняешь приёмку заново. В отчёте ссылайся на вердикты обоих агентов явно.

По ходу разработки быстрые проверки делай probe-скриптом (`npx tsx --conditions=development --env-file=.env <файл>.ts`) с замерами `process.hrtime()` (формат ниже). Probe-скрипты держи вне `src/` и удаляй; ценный сценарий оформи как e2e-тест в `tests/`.
Probe запускаем только через `tsx --conditions=development` (не голым `node ...ts`) — иначе `#`-импорты уходят в `dist/` и падают.
