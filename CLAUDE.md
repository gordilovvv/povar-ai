## О проекте

Проект для **вечеринок**. Цель — убрать ручную работу и автоматизировать
общение с гостями через AI-агента.

## Стек

typescript + pg + pg-format + zod + itty-router. Менеджер пакетов PNPM

## Код

### Функции
Где не нужен контекст (`this`) — пишем стрелочные функции, не `function`.

### Коментарии
Комментарии по дефолту не пишем. Можем написать только если видим, что логика плохо читается или какой-то неявный кейс.Также комментарии должны быть короткими и ясными. Запрещено делать комментарии на несколько строк.

План работы и TODO держим вне кода. Комментарий-«лесенку» из нескольких пунктов не пишем; максимум одна строка `// TODO: ...`.

### Структура и чистота
- Утилиты общего назначения не объявляем в рабочих файлах — выносим в `lib/` отдельным файлом с понятным именем.
- Где жить коду решает природа кода, а не число вызовов. Логика, привязанная к одному контексту, — рядом с ним. Универсальная утилита, не завязанная на контекст, — в `lib/` отдельным файлом, даже если потребитель пока один.
- Одноразовую линейную логику пишем инлайн — не выделяем функцию ради единственного вызова и не строим тонкие обёртки-цепочки. Это про локальную логику внутри функции; разбиение на слои остаётся обязательным даже при единственном вызове.
- Делаем ровно то, что просят. Меняем только названное; соседний код не трогаем, не переносим, не «улучшаем» заодно. Расширение scope — отдельным согласованием.
- Внешние/сырые данные не приводим к типу через `as` — парсим и валидируем (zod). `as` к доменному типу для непроверенных данных запрещён.
- Магические числа-параметры держим именованными константами рядом с местом использования; в конфиг выносим, только когда их реально нужно менять снаружи.
- Порядок в файле сверху вниз: основной флоу/хендлер — первым, вспомогательные функции — ниже него. Не заставлять читателя прыгать вверх к определениям.
- Инфраструктурное/транспортное (проверка подписи, парсинг протокола, низкоуровневый glue) — отдельным модулем, не инлайнить в бизнес-файл.
- Не плодим сущности: не заводим таблицу/колонку/абстракцию, если задачу решает существующая структура. Простейшая работающая модель побеждает; усложнение — обосновать, а не «так чище».
- Производное выводим из единого источника правды (например, карту весов — из порядка опций enum), а не дублируем литералы рядом.

### Состояние, гонки, идемпотентность

- Состояние и замки держим в данных/SQL, не в памяти процесса. Захват работы — одним атомарным `UPDATE … RETURNING`, который сам себе замок (без in-memory Set, без watermark):
- Оптимистичное обновление при гонке на запись одной строки (несколько источников могут писать одновременно): версия-колонка. Читаем версию, пишем `update … set …, version = version + 1 where id = … and version = <прочитанное> returning *`. Ноль затронутых строк = нас опередили → перечитать и решить (повтор/пропуск), а не слепо перезатирать.
- Явное > неявное: идемпотентность и гонки — через `try/catch` на конкретный код ошибки (нарушение unique), а не `on conflict do nothing`.
- select-or-create через рекурсию: `select` → нет → `insert` → на unique-нарушении вызвать функцию заново; верхний `select` перечитает победителя гонки. Терминируется: после нарушения строка точно есть.
- Не ретраить, когда повтор вреден по смыслу (устаревшее действие вклинится в ушедший вперёд поток) → терминальный статус (`failed`), не назад в очередь.

### Переменные окружения

- Читаем **только** из `environment.ts` (экспорт `env`). `process.env` напрямую в коде не трогаем.
- В `environment.ts` пишем проще: каждая переменная просто `z.string()` (или `z.enum`), **без `.default()`**. Дефолты маскируют отсутствие конфига и выстрелят в проде — пусть лучше падает на старте.

### Хендлеры

**Именование**
- Файл — в camelCase.
- Имя экспорта = имя файла + суффикс `Handler`.
- Хендлеры добавления/сохранения называем с префиксом `update` (не `set`/`save`/`add`).

**Структура**
- Валидация входа через Zod (`safeParse`) + ранний `return`. Любой `if` с блочными скобками — однострочные `if (...) return ...` запрещены.
- Маппинг данных делаем через `for...of` + `push` в константу, без отдельных функций-мапперов.

**БД и соединения**
- Все db-функции принимают `client: PoolClient` первым параметром; `pool.connect()` — в хендлере.
- Соединение не держим открытым во время внешних запросов: сначала db-операции в `try/finally` с `client.release()`, затем вызовы внешних API.

**Query и пагинация**
- Query-параметры парсим inline (`parseInt`/`parseFloat` + `|| default`), компактно в одну строку — без отдельных констант и блоков валидации.
- `limit` ограничиваем сверху через `Math.min(..., max)`, `offset` снизу через `Math.max(..., 0)`.

### DB
Когда пишешь или правишь DB-код — storage-слой (`src/db/`), SQL, таблицу, миграцию или ручку, которая ходит в базу — используй скилл `db-code`. Все конвенции там.

Запросы к базе выполняешь сам через `./scripts/db.sh` (обёртка над `psql`, берёт `DATABASE_URL` из `.env.prod`):
- `./scripts/db.sh "SELECT ..."` — выполнить SQL
- `./scripts/db.sh` — интерактивный psql

### Логирование производительности
Замер времени выполнения через `process.hrtime()` — вызов до и после операции, вывод через `console.log` с тегом `[модуль]`, идентификатором контекста, кратким описанием операции и временем в формате `Xs Yms`.

### Время

- Храним время UTC-строкой через `toDateTime`. Dubai (`getDubaiTime`) — только для показа агенту/человеку.
- Окна сравниваем в одном представлении: границу считаем тем же `toDateTime` (`toDateTime(Date.now() - N)`) и сравниваем со store-полем. Новую колонку-таймстамп ради окна не заводим.

## Воркфлоу диалога (из Figma)

Основная схема того, что делает агент. Источники трафика сходятся в WhatsApp,
дальше один сценарий диалога.

**Что бот знает на входе каждого диалога:**

- пришёл человек с рекламы (таргет) или нет
- какие вечеринки сейчас активны (одна / несколько, даты, локации)
- что он уже сказал в переписке

### Точки входа

```
[Таргет / реклама] (в рекламе зашито «Хочу в COYA, Дубай 🎉»)  ─┐
[Кто-то скинул номер / записывался ранее]                       ─┼─→ [Человек переходит в WhatsApp]
[Пишет в Instagram] → [«Привет бро, напиши мне в WhatsApp»]    ─┘
```

### Основной диалог в WhatsApp

```
[Человек в WhatsApp]
   ├─ пришёл с таргета, одна вечеринка → [Без вопросов переходим к шагу 2] → [Собрать данные]
   ├─ хочет на вечеринку → [«У нас две: [лок.1] пт и [лок.2] сб. На какую?»] → [Собрать данные]
   ├─ просто «привет» → [«Здарова бро, Йо»] (1-я реплика — тон, 2-я — к продаже) → [Собрать данные]
   └─ нерелевантное («дай рецепт борща») → [«Бро, есть гугл 🤣»]  (стоп)

[Собрать данные]
   ├─ [Уже знаем кто это] ─────────────→ [Тихо заносим в Guest List]
   └─ [Собираем Имя + инста] ──┬────────→ [Тихо заносим в Guest List]
                               └────────→ [Предлагаем стол 💵]

[Предлагаем стол 💵]
   ├─ отказ / «я подумаю» → бот не давит, закрывает позитивно через гест-лист:
   │        → [«Добавил тебя. До 12:00 вход бесплатный, после — 100 дирхам»]
   │          (цена входа и время берутся из данных вечеринки)
   └─ взял стол 💵 → [Показываем столы + цены] → [Узнаём кол-во человек]
            → [«Все супер бро, стол забронировал, увидимся на вечеринке»]
```

### Шаг сбора в гест-лист (формулировки)

- «Сейчас запишу тебя в гест-лист, пришли имя/фамилию»
- «Ты сам по себе или модель/блогер? У них свои условия»

## Что строим

Подключаем **API Instagram** и **API WhatsApp**, чтобы запустить агента,
который сам общается с людьми. Сценарии:

- Человек пишет «хочу на вечеринку» → агент отвечает, рассказывает про
  подходящую вечеринку.
- Человек отвечает на сторис (историю в Instagram) → агент реагирует и
  ведёт диалог.
- Перевод/отправка человека в WhatsApp для продолжения общения.

## Что автоматизируем (вместо ручной работы)

- Ответы на входящие сообщения и реакции на истории.
- Подбор и предложение конкретной вечеринки под запрос.
- Опись (учёт) людей.
- Добавление людей в гостевые списки (guest-листы).

## Архитектура агента

### Схема работы

```
Пользователь пишет
       ↓
   Webhook
       ↓
  Обработчик
       ↓
  Claude API (агент + MCP-инструменты)
       ↓
  Instagram/WhatsApp API (ответ)
```

### Почему MCP

Агент должен не просто отвечать, а делать вещи:

- `get_parties()` — найти подходящую вечеринку
- `add_guest(name, phone)` — добавить в гостевой список
- `check_guest(phone)` — проверить, уже в списке или нет
- `send_whatsapp(phone, template)` — отправить шаблонное напоминание

### Пример полного сценария

1. Пользователь пишет в Instagram: «хочу на вечеринку в эту пятницу»
2. Webhook получает сообщение → передаёт агенту
3. Claude вызывает `get_parties(date: "пятница")` → получает список вечеринок из базы
4. Claude отвечает пользователю, предлагает конкретную вечеринку
5. Пользователь пишет имя → Claude вызывает `check_guest` → `add_guest`
6. За день до вечеринки планировщик (cron) вызывает `send_whatsapp` с шаблоном-напоминанием
7. Пользователь отвечает «ДА» → открывается 24-часовое окно → агент продолжает диалог

### HTTP-хендлеры (itty-router)

- Файл-обработчик экспортирует сам handler (`RequestHandler`) именованным экспортом с описательным именем; роутинг подключается снаружи.
- HTTP-ответ возвращаем через хелпер `status()` из itty-router, не `new Response`.

### Каркас

- **Webhook.ts** — смотрит наружу, центральная бизнес-логика: получить сообщение → отдать агенту
- **Intelligence/** — `agent.ts` + все ручки в одной папке. Ручки: `getParties/checkGuest/addGuest/bookTable → db`, `sendWhatsApp → http`. Оборачиваются как tools. Каждая = как http-handler (zod → парсинг → базка → try/catch), SQL тут не пишем
- **DB** — pool + запросы
- **Promo.ts** — отдельный сервис: время Дубая, получить guests, фильтр, рассылка шаблоном
- **Platforms/** — интеграции: `whatsapp.ts`, `instagram.ts`
- **Lib/** — `time.ts` (время Дубая)

### Ключевые ограничения API

- **Instagram и WhatsApp:** агент не пишет первым — только отвечает на входящее
- **Окно ответа:** 24 часа с момента последнего сообщения пользователя
- **Исключение:** шаблонные сообщения WhatsApp можно отправлять в любое время (нужно одобрение Meta)
- **Разрешения Instagram:** `instagram_business_basic` + `instagram_business_manage_messages`
- **App Review не нужен** — аккаунт один, свой (Standard Access)
