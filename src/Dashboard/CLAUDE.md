# sema — админка (Dashboard)

Отдельный проект (`src/Dashboard/`): свой процесс, свои `Lib/`, `index.ts`-вход, `Db`/пул. С основным кодом не переплетаем. Общие конвенции — в корневом `CLAUDE.md`; здесь — специфика хендлеров/API и цикл приёмки.

## Handlers

Когда пишешь или правишь хендлер HTTP-запроса (новая ручка, файл в `Handlers/`) — используй скилл `http-handler`. Все конвенции там.

- Query/path-параметры парсим хелперами из `#Libs/Fmt.js`.
- Даты гоняем через `#Libs/Fmt.js`: наружу `fromDateTime`, в базу `toDateTime`, всё UTC. `.toISOString()` инлайном не дёргаем.

## Самотестирование при разработке

Закончил модуль, handler, либу или заметный кусок логики — **обязательно вызови скилл `e2e-test`** перед отчётом пользователю.

**Определение «готово» (жёсткое, в т.ч. для /goal-цикла):** модуль готов и цель выполнена ТОЛЬКО когда пройдены все шаги:
1. `pnpm typecheck` и `pnpm lint` зелёные (`node:test` гоняет TS без проверки типов — красный tsc проходит мимо зелёных тестов);
2. позитив написан автором, `pnpm test` зелёный;
3. `e2e-critic` (adversary) вызван, сам написал и прогнал `tests/<module>.attack.e2e.test.ts` (auth / IDOR / инъекции / кривой ввод / гонки, красный-первым) И прочитал позитивный тест автора на самообман (сверка с БД, не ослаблен ли ассерт/данные/бюджет) — вернул **ГОТОВО** по обоим;
4. `simplifier` вызван на дифф модуля и теста.

Пока `e2e-critic` не дал `ГОТОВО` — рапортовать «готово» и завершать /goal-цель запрещено. `НЕ ГОТОВО` = цикл не закрыт: чинишь код (не ослабляешь пробу) и гоняешь приёмку заново. В отчёте ссылайся на вердикты обоих агентов явно.

По ходу разработки быстрые проверки делай probe-скриптом (`npx tsx --conditions=development --env-file=.env <файл>.ts`) с замерами `process.hrtime()` (формат ниже). Probe-скрипты держи вне `src/` и удаляй; ценный сценарий оформи как e2e-тест в `tests/`.
Probe запускаем только через `tsx --conditions=development` (не голым `node ...ts`) — иначе `#`-импорты уходят в `dist/` и падают.

### Probe-бенчмарки вариантов
Если есть 2–3 варианта реализации с неочевидной производительностью — не выбирай «на глаз»: напиши один probe-скрипт со всеми вариантами, прогони с замерами `process.hrtime()` на реалистичном объёме данных, покажи таблицу сравнения и выбери лучший. Каждый вариант гоняй ≥3 раз, первый прогон отбрасывай (прогрев JIT/коннекта). Победителя — в код, probe — удалить (или ценный сценарий → e2e в `tests/`).

### Сверка с базой по ходу разработки
При разработке и отладке не гадай о состоянии данных — смотри базу через `./scripts/db.sh "SELECT ..."`: до прогона (исходное состояние) и после (что реально записалось). Ассерты в e2e тоже сверяй с фактом в БД, а не только с ответом API. После мутирующего теста проверяй не только целевую строку, но и что не наплодилось лишних (дубли при гонках).
