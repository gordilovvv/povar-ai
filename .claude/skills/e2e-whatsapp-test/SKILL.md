Механика браузера (snapshot, type_text) — скилл `chrome-devtools-cli`, команды не дублируй. Браузер здесь — только клавиатура гостя: один `take_snapshot` за сессию, чтобы взять uid поля ввода, дальше каждый ход — `type_text` + Enter. DOM не читаем и не ждём: ответ, конец хода агента и факт доставки живут в БД.

## Что это трогает

Твоё сообщение → вебхук → очередь → воркер → агент (реальный вызов модели) → Cloud API → БД. Живой прод-путь через настоящий WhatsApp Business номер Семы:

- Пишутся реальные строки в `wa_chats`, `wa_messages`, `guests`, `party_guestlist`; прогон стоит реальных вызовов модели и WhatsApp-отправок.
- Работай с отдельного тестового номера-гостя, насеянные строки чисти после.
- Не спамь: один осмысленный диалог дороже двадцати «привет».

## Ворота

- Номер Семы — `+971 58 687 7588`: реплики гостя отправляй именно в этот чат. Логин в WhatsApp Web — от пользователя; нет — спрашивай, не начинай.
- Система поднята, вебхук WA указывает на неё, и она живёт с `WA_SEND=on` — иначе исходящие в `wa_messages` не пишутся и свидетеля нет.
- Кейс «прощальный пузырь после pause_chat» действителен только при `TEXT_AFTER_PAUSE_CHAT=on` — проверь флаг до плана.

## 1. План переписки — от суб-агента, до чата

Кейсы не выдумывай сам — запусти суб-агента-разведчика (Explore/general-purpose). Дай ему тему пробы (гест-лист / бронь столов / живой разговор / другое); он читает код этой темы и задачу модуля и возвращает план: реплики боту по порядку + ожидаемое **поведение** на каждую (эффект в БД или тул-вызов, не текст ответа). Переписку ведёшь строго по плану.

Целься в то, что сломается молча (не «вежливо ответил», а «на имя завёл гостя ровно раз», «после `pause_chat` не пишет», «цифру назвал только из выдачи тула»), и включай негатив: пустой ввод, мусор, две реплики подряд, увод с темы.

## 2. Ход: type_text → SQL-ожидание

- Телефон гостя в запросах — в том виде, как он лежит в `wa_chats.wa_phone` (без `+`).
- До хода сними границу: `select coalesce(max(id), '') from wa_messages where wa_chat_phone = '<гость>'` (id — ULID, сортируется по времени; `coalesce` — иначе на чистом номере `id > NULL` не выполнится никогда).
- `type_text` реплику, Enter. Больше браузер в этом ходе не трогаешь.
- Жди SQL-опросом через `./scripts/db.sh` до условия, не по времени: твоя входящая строка (`owner='guest'`, `id >` границы) появилась И получила терминальный `worker_status in ('processed','failed','skipped')`. Ход кончается ровно одним из трёх:
  - `processed` — агент завершил ход; статус ставится после всего хода, значит все ответные пузыри уже в базе;
  - `skipped` — чат на паузе, входящее в обработку не пойдёт вовсе. Это легитимный свидетель кейса «после pause_chat молчит», а не зависание;
  - `failed` — агент/API упал, см. красное. Ответом это не считается, даже если пузыри частично легли.
- Воркер берёт сообщение с дебаунсом ~5с — первые опросы пустые, это норма.
- Ответные пузыри — строки `owner='sema'` с `id >` границы. Пусто при `processed` — почти всегда дефект (обрыв по `max_tokens` или ход без ответа): легитимного молчания с `processed` в коде нет — пауза даёт `skipped`, а `pause_chat`/`save_guest` отвечают сами. Не пере-отправляй, иди в красное п.4.
- Реплики по одной, жди терминального статуса на каждую. Кейс «две реплики подряд» — исключение: шли обе быстро (дебаунс 5с, медленный второй `type_text` разорвёт батч) и потом проверь SQL, что склейка состоялась — между id двух входящих нет строки `owner='sema'`. Есть — ходы разделились, кейс не состоялся, повтори быстрее.

## 3. Ассерты — только SQL

- Текст ответа — из `wa_messages.text`, не из DOM.
- Эффекты тулов — `guests` / `party_guestlist` / `wa_chats.paused_at`: до хода исходное состояние, после — что записалось и что не наплодилось лишнего (дубли).
- Доставка — отдельным опросом с бюджетом ~60с (статусный вебхук приходит позже `processed`): `status in ('delivered','read')` у исходящей. Именно так: `read` может прийти раньше и перекрыть `delivered` навсегда, а «статус вырос» без списка засчитает `failed` за доставку — у него высший ранг. `failed` — красное про доставку, не про агента.

## 4. Оценка: частота, не булев гейт

Генеративный агент на один ввод отвечает по-разному — один прогон ничего не решает. Спорный кейс гоняй ≥3 раз: `3/3` — стабильный дефект, чини `src/`; `1/3` — разброс генерации, не баг. Верь сигналам по убыванию: эффект в БД → трейс тулов → словарные линтеры → в крайнем случае смысл текста. Ценный сценарий оформи пробой в `tests/probes/arena/` (формат — память `sema-generative-test-format`).

## 5. Красное: сначала исключи инструмент

1. Входящей строки нет → сообщение не дошло до вебхука: не тот чат/номер, WA Web разлогинен, вебхук смотрит не на эту систему.
2. Висит `need_processed` сильно дольше дебаунса (>~15с) → воркер не запущен, либо чат держит `processing` другого хода. Висит `processing`, а строки `owner='sema'` уже легли → воркер ретраит запись статуса, ход состоялся — жди, это не дефект.
3. `failed` → упал агент/API/тул, не дефект поведения. Реплика могла реально уйти гостю без строки в БД (отправка идёт до вставки) — тут один взгляд в чат глазами и в логи воркера обязателен до вердикта.
4. `processed`, исходящей нет, а план ждал ответ → смотри `wa_chats.paused_at` и логи воркера; только потом — дефект агента.
5. Исходящая застряла в `sent` дольше бюджета → доставка/статусный вебхук, не агент.

Только после 1–5 — дефект агента, описывай с диагнозом (промпт/тул/факт). Три хода без сдвига — стоп, доложи.

## 6. Зубы и самообман

Ассерт не ослабляй под фактический ответ — дефект чинится в `src/`, не понижением кейса. Проверь кейс на пустоту: отправь то, на что правильно — отказ/вопрос. Агент всё равно «уверенно записал»? Кейс не проверял ничего, усиль провокацию. Ассерт `count>0` не умеет не выполниться — сверяй содержимое и направление.

## 7. Отчёт человеку

- кейсы словами задачи; по каждому поведение + сверка с БД (что легло, дублей нет), частота слома `n/3`;
- чего проба не видит: другой прогон ответит иначе, прод-БД дрейфует, рендер чата в WA Web (мы его не читаем);
- красное с диагнозом; что насеял и что вычистил.

Вердикты: `GREEN` (поведение и БД сошлись) | `RED` (дефект агента, диагноз) | `ASK` (нужен человек: логин, номер, факт).
