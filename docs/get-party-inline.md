# Схлопывание get_party: факты вечеринок в контекст

Статус: план, не реализовано. Контекст: разбор латентности первого турна повторного гостя (проба `ReturningSoloDialog`, 52.8с).

## Принцип

**При проектировании агента оптимизировать надо глубину цикла, а не длину промпта.**

Разложение турна 52.8с: ~95% времени — генерация thinking-токенов на «думающих» шагах (step 0 ≈ 32с, step 1 ≈ 19с), а весь system-промпт (~4.5k токенов) читается из кэша и почти не влияет на латентность. Каждый тул-шаг = полный запрос к модели с полным thinking-циклом: на `effort: max` это +15–30с. Лишняя тысяча токенов в кэшированном промпте ≈ бесплатна по времени.

Следствие для дизайна тулов: read-only тул с маленьким детерминированным результатом — это round-trip за данными, которые можно было отдать в промпте. Тул оправдан для *действий* (send_message, save_guest, pause_chat) и для данных, зависящих от решения модели или слишком больших для контекста. `get_party` — ни то, ни другое: `Context.load` уже выполняет тот же `selectActivePartiesWithTimes`, что и хендлер тула, но до модели доходят только имя и party_id (строка `parties running` в Checklist).

`get_party` проектировался как lazy-загрузка («модель спросит, когда надо»). Замер показал: почти каждый значимый турн (питч, любой вопрос о вечеринке) проходит через него — lazy надо превратить в eager.

## Решение: убрать get_party, данные в контекст

Карточки активных вечеринок рендерятся во **второй** (некэшируемый) system-блок — тот, что собирает `Checklist.create`. Тул `get_party` удаляется.

Формат карточки не проектируем заново: берём ровно ту структуру, что возвращал хендлер (`GetParty.ts:32-69` — `party_id, name, type, location, price, notes, reels_url, google_map_link, when[]`), цикл группировки переносим как есть, выводим `JSON.stringify` одной строкой. Модель уже настроена на эту форму — нулевой дрейф поведения; заодно снимается ловушка `state.join(' | ')` (`Checklist.ts:92`), куда многострочная карточка не влезает. Язык — `guest.lang ?? 'en'`, как уже сделано для past parties (`Checklist.ts:99`).

Выигрыш: −1 модельный шаг на каждом питч-турне (здесь −32с, турн 52.8с → ~21с), −~400 токенов описания тула из схемы, минус одна сущность.

Цена: +300–500 токенов в некэшируемом блоке каждого запроса (по времени ≈ ноль).

Отвергнутый вариант (данные в контекст + тул оставить как fallback): модель, приученная звонить перед питчем, продолжит вызывать тул «на всякий случай» — латентность не уйдёт, появятся два источника правды.

## Оговорки

1. **Масштаб.** Сейчас активных вечеринок 1–2. При 5–10 параллельных блок распухнет — тогда lazy-тул вернётся как правильное решение.
2. **Пустой результат.** В описании тула было правило «пустой результат = открытых вечеринок нет, так и скажи, не выдумывай». При нуле активных вечеринок блок пустой — правило перенести, иначе модель достроит вечеринку. Общая защита от выдумывания уже есть в `system.md:64,69,73` — её не дублируем.
3. **Локализация.** get_party отдавал weekday на языке гостя, который заполняла модель; в блоке язык берётся из `guest.lang` (детект кода, `Context.ts:54-64`) и при недетекте будет `en`-формат (`Sunday 15.03 9:30pm` вместо `воскресенье 15.03 21:30`). Осознанная регрессия, отдельного фикса не делаем.
4. **Кэш-граница.** Карточки — только во второй блок (`Agent.ts:197-204`). В первом (кэшируемом) смена вечеринок инвалидирует весь prompt-кэш.

## План реализации

1. **`Checklist.ts`**: `running()` (`:112-118`) → JSON-карточки (тело группировки скопировано из `GetParty.ts`, даты через `formatDubai(..., guest.lang ?? 'en')`); строка `parties running` уходит из `state[]` (`:46`) — карточки идут отдельной строкой в `lines` рядом с `Past parties:`, второго источника того же списка не оставляем; `Now: 'greet + pitch (get_party)'` (`:72`) → `'greet + pitch'`.
2. **Код**: удалить `Tools/GetParty.ts`, убрать импорт и элемент из `Tools.ts`; удалить мёртвый второй реестр `Tools/index.ts` (никем не импортируется, но без правки уронит компиляцию). `selectActivePartiesWithTimes` остаётся — им пользуется Context.
3. **Точечные замены `get_party` → «the party facts block»**, без переписывания абзацев:
   - `tools.md:4` — строку удалить; `tools.md:8` — убрать скобку «(get_party has entry price only)», остальное оставить;
   - `system.md:44`, `system.md:68`; `system.md:64` («Links only from tools») — ссылки теперь приходят из блока, формулировку поправить;
   - `new-guest.md:6`;
   - `SaveGuest.ts:22` (описание) и `SaveGuest.ts:54` (инструкция ошибки `unknown_party` велит вызвать get_party — после удаления тула это указание на несуществующий тул, обязательная правка → «party_id из блока фактов»);
   - `SendMessage.ts:14`, `PauseChat.ts:13`.
   - `known-guest.md` не трогаем: `get_party` там не встречается.
4. **Пробы**: полный прогон `e2e-whatsapp-test`, обе пробы (новый гость, повторный). Критерии сверх обычных: (а) модель не выдумывает отсутствующие факты и не выдумывает вечеринку при пустом блоке; (б) питч содержит реальные дату/место/условия из блока; (в) замер времени первого турна до/после.

Не трогаем: `Agent.ts`, `Context.ts`, `Db/Party.ts`, `known-guest.md`. Новых правил поведения в промптах не вводим — «ask which» уже есть (`new-guest.md:6`), заморозка контекста на турн уже описана в JSDoc `Context.refresh`.

Замер `effort: max` vs `high` — отдельная работа, в этот план не входит: смешивать эффекты двух изменений в одном замере нельзя.
