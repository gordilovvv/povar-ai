# Чек-лист агента — утверждённая бумага

Статус: утверждён 2026-07-21. Только дизайн, в коде не реализовано.

Документ описывает **шаги воронки**. Форма машинного блока состояния, который
подаётся модели каждый ход, — в `AGENT-STATE.md`.

---

## Шаги (`checklist.md`, статичный файл)

```
## Flow (in order; skip what "Done" lists)
1. Greet. From ad/referral → jump to 3.
2. Pitch parties once. More than one party → ask which one.
3. Name: "пришли имя фамилию". Guest brings +1 → get each companion's name.
4. Ask instagram once (optional) AND add_to_guestlist in the SAME turn —
   never wait for the answer, never re-ask. Confirm + entry conditions.
5. Unprompted after the confirm, once: our instagram + WhatsApp group.
6. Offer a table once. Any table interest → "по столам скоро вернусь"
   + table_response(agreed). Refusal → warm close + table_response(declined).
   Never book yourself.
```

## Правила формы

| Правило | Почему |
|---|---|
| Текущий шаг — ровно **один**, всегда | второй одновременный шаг теряется 15/15 (проба 6) |
| Марок нет ни одной | `Done` + `Now` несут то же без легенды |
| Марка «спросили-ждём» мертва | под ней нет факта в базе; дублирует `system.md:36` |
| Марка «запрещено» мертва | догадка со статусом закона — это был баг |
| Строки не исчезают | каркас стабилен, шаги видны всегда |
| Инструкций в блоке состояния нет | политика живёт в `system.md`, состояние — только факты |
| Ничто не объявляется нерушимым | если под этим нет строки в базе или вызова тула |

## Что изменилось против сегодняшнего кода

- пять марок (`[✓] [→] [ ] […] [✗]`) → ноль
- две одновременные стрелки → один указатель
- пять строк с вшитой политикой → шесть чистых шагов
- исчезающая строка про стол → постоянная
- бронь ботом (`book_table`) → пауза и подключение человека

## Принятые решения владельца

**Инстаграм необязателен.** Решение с доски в FigJam, принято как есть.
Риск зафиксирован: сбор инсты упадёт с «почти все дошедшие» до «кто сам захотел».

Следствие для этапа реализации: гейт в `AddToGuestlist.ts:24-26` и текст описания
тула (строка 9, «Requires the guest's own instagram saved first») придётся снять.
Иначе `checklist.md` и инвентарь тулов противоречат друг другу, и модель послушает
инвентарь — он ближе к действию.

**Шаг 5 (наша инста + WhatsApp-группа) остаётся.** На доске его не было, но он
работает в проде и это единственный бесплатный канал удержания. Дефолт — сохранить;
выкинуть потом дешевле, чем восстанавливать.

## Что живёт не здесь

Правила поведения — в `system.md`, не в чек-листе:

- «отвечает только на то, что знает»
- «про стол — скоро вернусь»
- «в остальных случаях позову Сёму»

Это не шаги воронки. Дублировать их в двух файлах — заводить два источника правды.

## Спутники (`+1`)

Спутники — не самостоятельные гости: нет телефона, нет чата, не получают сообщений,
не живут между вечеринками. Привязка к записи на вечеринку, а не к гостю — один и тот
же человек в субботу приходит с женой, через неделю с друзьями.

Два поля на `party_guestlist`:

| Поле | Смысл |
|---|---|
| `companions_total int not null default 0` | сколько спутников заявлено гостем |
| `companions text[] not null default '{}'` | имена, которые уже собрали |

Два поля, а не одно, потому что «заявлено двое» — это тоже факт. Хранить только
собранные имена значит оставить число спутников в тексте переписки и снова угадывать
его поиском по чату. Заявленное число ставит вызов тула.

Машинно проверяемое условие: шаг 3 остаётся текущим, пока `named < declared`.

## Известные дыры

- Развилка «какая вечеринка?» — без `party_id` гест-лист невозможен. Шаг 2 обязан
  её содержать; в исходном наброске её не было.
- Схема под спутников не мигрирована — поля выше пока только на бумаге.
